CASE STUDY // LIMS IMPLEMENTATION // LAB INFORMATICS

From bench to LIMS.

I was the lab-side lead on a LIMS implementation in a regulated medical-device QC lab. I wrote the requirements, turned SOPs into system workflows, validated the system and trained the people who use it. This page covers what I did, what I took from it, and a working demo of the kind of data tooling I build on top of a LIMS.

// 01 THE STORY

A lab that ran on records, and a system that had to match how the lab actually works.

QC Microbiology tests have to happen on a defined schedule, results have to be reviewed, and every record has to stand up to an audit. A LIMS only helps if the system's workflows match how the lab really works, and if the people using it trust it.

When the lab moved to LIMS 2.0, I represented the people who run the tests. My job was to make sure the system did what the SOPs say, that we could prove it, and that the team could use it on day one.

// 02 WHAT I DID
01
Defined user requirements
Captured what QC Microbiology needs from the system: what gets tested, when, by whom, and what has to be recorded.
02
Turned SOPs into workflows
Translated written procedures into system workflows, and redlined SOPs where the system and the document needed to agree.
03
Validated the system
Executed validation test scripts and reviewed critical calculations, audit trails and data security before go-live.
04
Migrated history
Led the move of five years of microbial identification records from paper logs into the LIMS.
05
Trained users after go-live
Taught the team to work in the new system and fielded the questions that only show up once real samples are flowing.
06
Built the reporting layer
Wrote and maintain SQL against the LIMS data and own Power BI reports that track testing volume and turnaround against SOP-defined frequencies.

C. The SQL behind panel A

A generic example of the aggregate behind the trend. Table and column names are illustrative, not from any real system.

SELECT
    zone,
    DATE_TRUNC('week', sample_date) AS week_start,
    SUM(cfu_count)                  AS weekly_cfu,
    MAX(alert_limit)                AS alert_limit,
    MAX(action_limit)               AS action_limit,
    CASE
        WHEN SUM(cfu_count) > MAX(action_limit) THEN 'ACTION'
        WHEN SUM(cfu_count) > MAX(alert_limit)  THEN 'ALERT'
        ELSE 'OK'
    END AS status
FROM em_results
WHERE sample_date >= DATEADD('week', -52, CURRENT_DATE)
GROUP BY zone, week_start
ORDER BY zone, week_start;
// 05 WHAT I TOOK FROM IT
The best requirement comes from the person at the bench.
A system that matches the SOP on paper but not the actual workflow gets worked around. Sitting with the people who run the tests mattered more than any template.
Validation is documentation of trust.
Running scripts is the easy part. Explaining clearly what you tested, why, and what the evidence shows is the part auditors and teammates actually read.
Reporting is where a LIMS earns its keep.
Once data is in one place, a good query and a clear dashboard turn it into early warning. That is the part I most enjoy and want to do more of.
I want to bring this to other labs.
I know what it is like to be on the receiving end of a LIMS rollout. I would like to be the person helping other labs get through theirs.
